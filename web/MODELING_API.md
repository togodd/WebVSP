# Internal modeling API: design and implementation status

This document defines the scope and safety rules for WebVSP's browser-local modeling service. It is not an MCP server or a remote-control endpoint. OpenVSP running in the current tab remains the authoritative model; a service must not maintain a second geometric model.

## Delivery sequence

Each increment is committed separately, after its tests pass. Existing GUI behavior and uncommitted work must be preserved. Capabilities are exposed only when implemented and tested; proposed operations below are not promises of current support.

1. Establish typed contracts, explicit capabilities and errors, and an injectable engine adapter. Add fast contract tests.
2. Add read-only model, geometry, selection and bounds queries. Validate their behavior against the real browser engine and GUI updates.
3. Add selected basic writes only where results can be verified. Validate input and explicit parent identity; report before/after and unknown outcomes honestly. Exercise persistence and conflicts.
4. Investigate and, where safe, add parameter discovery, readback and controlled writes; then add narrowly scoped wing, fuselage and attachment operations. Operations with unverified semantics stay unavailable.
5. Run unit, integration and browser regression suites, document supported operations, and add a final verification record. MCP protocol, transport, remote access, AI and arbitrary file paths are out of scope.

## Contract principles

- Inputs and results must be serializable, versioned where externally useful, and independent of FLTK widget IDs or screen coordinates.
- Geom names are not unique identifiers. IDs are scoped to a live model and must not be assumed stable after reload, replacement, copy, or structural edits.
- Expose unavailable or unknown information as such. Native unit conventions are not inferred; report coordinate frames and model-native values explicitly.
- A completed request is not proof of the requested geometric effect. For writes, validate, execute, and read back actual state. If a timeout or interruption makes the result uncertain, do not claim failure or retry blindly.
- A parent-child tree relation does not imply translation or rotation attachment.
- Do not assert transactionality, rollback, or undo unless that specific operation has been verified. Multi-step partial execution must be reported.
- Model revision and dirty/undo fields in the current engine are bookkeeping, not established strong concurrency or persistence guarantees. Atomic revision checks require engine-side implementation and tests covering GUI changes; client-side checks alone cannot provide them.
- Browser sessions and model replacements need explicit identity. Do not conflate a page lifetime, a file name, and a model identity. If trustworthy replacement detection cannot be implemented, expose that limitation rather than inventing a guarantee.
- Schema and capability definitions must match the running implementation and tests. Never advertise a planned feature as supported.

## Current baseline

The existing `src/api/client.ts` provides model tree, geometry types, bounds, selection, origin, move, rotate and duplicate calls. `src/api/wasmEngine.ts` also routes add, delete and parameter writes. Those are implementation primitives, not yet a safe domain API. Engine requests and GUI events share an OpenVSP thread, but `engine.cpp` revision detection is based on polling and fingerprints, and the model response currently contains a placeholder undo state. The legacy unscoped parameter write returns a generic acknowledgement; the separate scoped engine operation performs validation and readback, but is not enabled through the guarded facade. These facts prohibit assuming atomic concurrency protection, complete undo, or validated readback.

## Implemented interface and limits

Import `createBrowserModelingService` from `web/frontend/src/modeling`. `capabilities()` reports supported model, geometry, parameter, wing and fuselage reads; it describes the facade, not engine readiness. The browser engine needs a secure context with `crypto.randomUUID`; handles share an engine-module session ID.

Call `model.getInfo()` without an identity to obtain `identity: { sessionId, modelEpoch }` along with the model information. An optional identity can instead guard `getInfo` against replacement. Every other facade read (`model.getSelection/getVisibleSurfaceBounds`, `geometry.list/get`, parameter reads, `wing.get` and `fuselage.get`) requires an explicit identity. Retain and pass that identity with geometry and parameter IDs; reacquire it and discard old references after replacement. Invalid identities are rejected, and mismatched session or epoch is reported as `STALE_MODEL`.

The epoch is a decimal uint64 string, sampled with the model response. Guarded engine jobs compare it on the OpenVSP thread before executing. `Vehicle::Renew` and `Vehicle::ReadXMLFile` increment it, including before a read that may fail; overflow invalidates it rather than wrapping. This catches replacement paths only insofar as they pass through those hooks: it is not a guarantee that every possible model replacement is detected. It is not a model revision, lock, CAS, or transaction isolation: ordinary edits, GUI Insert and synchronous script reentrancy may occur without an epoch change, and multi-job reads are not atomic. Deleting all geometries and then inserting new ones can replace the visible geometry set without replacing the Vehicle or changing the epoch.

`getVisibleSurfaceBounds` covers shown geometry with a surface or mesh, not necessarily all geometry or actual rendered visibility. Its read is separate from model reads. `shown` means membership in OpenVSP's shown set, not necessarily rendered. `engineRevision` is an approximate watcher event counter: even equal values do not imply identical state, and it cannot serve as CAS, a transaction revision, or a complete event log.

Parameter discovery returns only OpenVSP's linkable geometry/XSec lists. A parameter's owner is checked against the live model on each engine request; `active` is not a complete editability guarantee, numeric null means the engine reported a non-finite number, and metadata does not identify units. XSec indices/surfaces are not equivalent to wing section indices. Reads are separate and do not form an atomic snapshot.

These reads are not strictly side-effect-free: requests also consume OpenVSP's global API error stack. Geometry parameter enumeration calls OpenVSP's `AddLinkableParms`: geometry implementations may pass their ID into nested containers, overwriting each encountered parameter's in-memory link-container ID. This can also happen during geometry-scoped parameter read/ownership checks, fuselage length lookup, and the engine's change-detection fingerprints; a failed request can have already performed enumeration. Direct XSec enumeration passes an empty ID through the XSec/curve path and does not itself overwrite those IDs. The link-container ID is distinct from the parameter's owning container reported in metadata. It is used by OpenVSP for link names and group/component linking, and by Snap To to resolve a geometry, so changed IDs can affect subsequent operations; the effect depends on prior state and later enumerations. Enumeration does not itself set parameter values or create links, and the setter for this ID does not itself notify the watcher or establish an undo step. Do not infer a model revision, dirty flag, undo record, persistence effect, or a guaranteed visible change from this bookkeeping mutation. Real-engine interaction and persistence consequences remain unverified.

`write.create`, `write.move` and `parameter.set` are present in the facade but **unsupported**: after identity validation they return `UNSUPPORTED_OPERATION` without dispatching a write. They are disabled pending review of synchronous script reentrancy, which can invalidate assumptions even within a guarded engine job. The lower-level guarded write path has a conservative context preflight and stages its result behind an explicit ScriptMgr execution guard, but the guard is not a general AngelScript VM barrier or proof of safety. Disposable WASM tests show that both explicitly triggered AngelScript garbage collection and releasing a script object's final reference (with automatic GC disabled) can run a script destructor that deletes a geometry without setting the guard's attempted flag. These tests do not establish that ordinary guarded writes trigger either path. If it blocks an attempt after mutation begins, the outcome is unknown and must not be retried automatically. An uncaught C++ exception after mutation can terminate the engine without a result; callers must treat a lost response as unknown. Wing driver choices, fuselage section transformations and translation/rotation attachment are also not exposed as semantic writes. Geometry tree parenting alone does not configure attachment.

The facade guard is not a protection for legacy low-level engine requests, existing GUI operations, or independently exported adapter services. Those interfaces can still mutate the model and must not be treated as guarded by this facade. In particular, a successful low-level guarded `move` result only reports that the underlying call did not report an API error; it does not prove that the requested displacement occurred. OpenVSP may skip small local components or clamp position parameters; disposable production-WASM tests observed both no-op cases reporting success. Independently exported services are experimental and are not a substitute for the disabled facade. No rollback, complete undo, persistent save, idempotency, or isolation guarantee is made. Closing a handle does not shut down the engine or cancel reads already initiated: a read waiting for engine startup may still be dispatched after close and may have the bookkeeping effects described above, even if its caller receives `SESSION_CLOSED`. There is no automatic timeout, so a stalled request can remain pending until the handle is closed.

File loading and saving are excluded from the facade. Low-level file operations use the in-memory filesystem and the GUI file path is separate. On detected open errors the low-level path marks the model dirty: it clears the existing model before reading and does not roll back. Write errors do not clear dirty state, but a filename may already have been changed; successful in-memory writes alone do not prove durable browser or disk persistence. Error detection itself is limited to errors surfaced by the underlying APIs.

## Testing and verification limits

The modeling directory contains contract and adapter-service unit tests, including tests for read, parameter, write, wing and fuselage services. Tests of independently exported write services do not imply that the browser facade enables writes or that legacy operations are guarded. Unit tests and mocked adapters do not establish real-engine or GUI replacement coverage, synchronous-reentrancy safety, transaction isolation, or durable file round trips. These require targeted engine and browser integration tests, including failed opens and save/reopen behavior; no such verification is claimed merely by this document.

## Acceptance

The first end-to-end scenario is to create a fuselage and explicitly parent a wing, move it, compare engine and GUI state, save, reopen and verify. Parent attachment is a distinct feature and is not implied by the tree. Parameter and domain operations need their own positive, invalid-input, stale-reference, GUI-interference and persistence tests. Any capability that cannot meet its stated contract remains unsupported and its specific blocker is documented.
